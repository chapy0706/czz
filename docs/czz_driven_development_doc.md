# czz アプリ開発における「〇〇駆動開発」の立ち位置整理

## はじめに

このドキュメントは、czz アプリ開発を題材として、近年よく使われる
**〇〇駆動開発（Spec / DDD / TDD / ADD / AI 駆動）**
それぞれの考え方と、czz がどの立ち位置にあるのかを整理するための教育用資料である。

単なる用語説明ではなく、

- なぜその開発スタイルが生まれたのか
- czz では「どこまで」取り入れているのか
- 今後どこを強化すれば名乗れるのか

を理解することを目的とする。

---

## 1. スペック駆動開発（Spec-Driven Development）と czz

### スペック駆動開発とは

スペック駆動開発は、

- 実装より先に **外部から観測できる仕様（振る舞い）** を定義する
- その仕様が **テストや契約として実行可能** である
- 実装は「仕様を満たす手段」にすぎない

という思想を持つ。

UI や内部構造ではなく、
「入力に対して、どのような結果が返るべきか」
を中心に設計を進める。

### czz の立ち位置

czz では以下がすでに存在している。

- dslProgram（何を実行するか）
- testCases（どうなったら正解か）
- evaluator（正誤を機械的に判定）

これは **仕様がテストとして存在している状態** であり、
スペック駆動開発に非常に近い。

#### 評価

- 現状：**準スペック駆動**
- 強み：仕様がコードより先に存在できる構造
- 今後の強化点：

  - スキーマ仕様の明文化
  - 互換性ルール（破壊的変更の扱い）の明示

---

## 2. ドメイン駆動開発（DDD）と czz

### ドメイン駆動開発とは

DDD は「Entity を作る手法」ではない。
本質は、

- 複雑さの中心を **ドメインモデル** に集約する
- 言葉（ユビキタス言語）を **コードと会話で一致させる**
- 技術都合より **業務・問題領域の意味** を優先する

という思想である。

### czz の立ち位置

czz は以下の点で DDD と親和性が高い。

- Domain / UseCase / Infra の依存方向が明確
- Repository interface が domain 側にある
- UseCase がアプリケーションロジックを担う

一方で、戦術的 DDD（Aggregate, ValueObject など）を
厳密に使い切っているわけではない。

#### 評価

- 現状：**ライト DDD**
- 強み：DDD を適用できる土台が完成している
- 今後の強化点：

  - 不変条件（invariant）の明示
  - ResultStatus などの意味を値として扱う設計
  - 用語の一貫性をドキュメントとコードで揃える

---

## 3. テスト駆動開発（TDD）と czz

### テスト駆動開発とは

TDD は「テストを書くこと」ではない。
本質は開発リズムにある。

1. 失敗するテストを書く（Red）
2. 最小実装で通す（Green）
3. 設計を整える（Refactor）

この循環によって、
設計と理解を同時に深めていく。

### czz の立ち位置

czz は以下を備えている。

- Unit（Vitest）
- E2E（Playwright）
- DSL 評価そのものがテスト構造

つまり **TDD を自然に行いやすい構造** になっている。

#### 評価

- 現状：**TDD 可能な設計**
- TDD と言い切れる条件：

  - 新機能・新コマンド追加時に Red → Green → Refactor を実践しているか

---

## 4. ADD（Agile Document-Driven Development）と czz

### ADD とは

ADD は、

- 重い設計書を最初に作らない
- しかし **意思決定と方向性が失われない程度のドキュメント** は残す
- ドキュメントもコードと一緒に育てる

という現実的な開発スタイル。

### czz の立ち位置

czz ではすでに、

- 進捗サマリ README
- アーキテクチャ方針
- ディレクトリ構成説明

が存在し、「引き継げるドキュメント」になっている。

#### 評価

- 現状：**ADD の入口**
- 強化すると良いドキュメント：

  - スキーマ仕様（Spec）
  - ADR（なぜその設計を選んだか）
  - 運用・テスト手順（How to run）

---

## 5. AI 駆動開発（AI-Driven Development）と czz

### AI 駆動開発の 2 つの意味

1. ツール駆動型

   - AI にコードを書かせる、修正させる

2. 構造駆動型

   - AI が理解・判断しやすい構造を先に作る

### czz の立ち位置

czz は明確に **構造駆動型 AI 開発に向いている**。

- 入力が構造化（JSON DSL）
- 正解条件が明示（testCases）
- 評価が機械判定
- 副作用が分離された設計

#### 評価

- 現状：**AI 補助前提でも壊れない設計**
- AI 駆動と呼べる段階：

  - 仕様生成・テスト生成・ADR 草案を AI に任せる運用に入ったとき

---

## 6. 総まとめ：czz の現在地

| 観点         | 評価                     |
| ------------ | ------------------------ |
| スペック駆動 | 準拠している             |
| DDD          | ライト DDD               |
| TDD          | 実践可能な設計           |
| ADD          | 入口に立っている         |
| AI 駆動      | 構造的に非常に相性が良い |

### czz の特徴的な立ち位置

czz は「〇〇駆動を名乗るために作られたアプリ」ではない。
**良い設計を突き詰めた結果、複数の駆動開発と自然に噛み合った構造** を持っている。

そのため教育用途として、

- 設計思想の説明
- 開発スタイルの比較
- 将来拡張（AI 活用）の議論

すべてに使える教材になっている。

# Spec: コマンドの数値入力をコマンドライン表示へ即時反映（プレビュー同期）

- Issue: TBD
- Status: active
- Updated: 2026-02-15
- Owner: TBD

## Goal（勝利条件）

コマンド編集で数値（例: 回数/秒数/行数など）を入力したとき、その値が **コマンドラインのパネル表示** にも反映されるようにする。  
ユーザーが「今のコマンドはこうなる」を目で確認しながら編集できる状態にする。

## 背景

- 現状、コマンド編集で数値を入れても、コマンドライン（疑似端末側）の表示が古いままで、学習者が混乱しやすい。
- “入力した値が反映されている” というフィードバックは学習体験の中核。遅延・不一致は認知負荷になる。

## Non-goals（やらないこと）

- DSL実行/評価ロジック（`packages/dsl-core`、UseCase）の仕様変更
- API/DB の変更
- 新しいUIコンポーネントの大規模導入（ライブラリ追加など）
- 表示の国際化対応（別Issue）

## Scope（変更対象の当たり）

最終確定は /codex の探索でよいが、影響が高い領域は以下。

- Command Builder（コマンド編集）
  - `apps/user/src/lib/command-builder/CommandEditorSheet.tsx`
  - `apps/user/src/lib/command-builder/CommandRow.tsx`
  - `apps/user/src/lib/command-builder/CommandBuilder.tsx`
  - `apps/user/src/lib/command-builder/*store*.ts`（Zustand等がある場合）

- コマンドライン（疑似端末/Runner/表示整形）
  - `apps/user/src/lib/terminal/PseudoTerminalRunner.tsx`
  - `apps/user/src/lib/terminal/*format*.ts`（表示用の整形関数がある場合）
  - `apps/user/src/lib/terminal/*store*.ts`（表示が別ストアなら）

- E2E（該当があれば更新）
  - `e2e/tests/command-builder-*.spec.ts`
  - `e2e/tests/pseudo-terminal*.spec.ts`

## 仕様詳細

### 1) 「数値入力」の定義

- コマンド編集画面で、ユーザーが数値（number）を入力するUI（input/stepper等）
- 対象は特定コマンドに限定しない（数値パラメータを持つコマンド全般）

### 2) 反映されるべき表示箇所

- 課題画面の「コマンドラインのパネル」上で、コマンドを文字列として見せている箇所
- 例:
  - `... --count 3` のような引数
  - `sleep 5` のような数値
  - DSLに依存せず、「ユーザーが見て期待する文字列」に反映されること

### 3) 反映タイミング

- ユーザーが数値を入力した時点で、コマンドライン表示も追従する（即時反映）
  - 推奨: `onChange` での反映（体感のズレが最小）
  - ただし性能が厳しい場合は軽い debounce（50〜150ms程度）を許容

### 4) 編集確定/キャンセルの整合性（重要）

コマンド編集に「保存/キャンセル」の概念がある場合、以下で破綻しないこと。

- 編集中: コマンドラインは **編集中のドラフト** を表示する（プレビュー）
- 保存: ドラフトが確定し、そのままコマンドライン表示に残る
- キャンセル/閉じる: コマンドライン表示は編集前へ戻る（ドラフト破棄）

実装方針（推奨、破壊が少ない）:
- ストアに `editingCommandId` と `commandDraftById`（または `editingDraft`）を持ち、
  - コマンドライン表示は「編集中のコマンドだけドラフト優先」で整形する
- もし保存/キャンセルが無く “即時反映が正” の設計なら、既存仕様に合わせて常に更新でよい

### 5) 表示整形のルール

- 数値は入力した値をそのまま表示する（丸め/フォーマット変更を勝手にしない）
- 未入力（空）の場合は、既存仕様に合わせる
  - 例: プレースホルダ表示のまま / 引数を出さない / 0 扱い など（現行仕様を維持）
- 不正値（NaN, Infinity, 負数など）は UI 側バリデーションで防ぐ（最低限）
  - コマンドライン表示は `unknown` を受けても落ちない（安全側）

## Acceptance Criteria（受け入れ条件）

- コマンド編集で数値を変更すると、コマンドラインのパネル表示にその数値が反映される
- 反映は “体感で遅延がない” レベル（即時、または軽い debounce）
- 編集に保存/キャンセルがある場合:
  - 保存で確定、キャンセルで元に戻る（表示も一致）
- 既存の実行結果や評価処理が壊れない（DSL実行は同じ入力で同じ結果）
- `make verify` が通る（必要ならE2E更新を含む）

## リスクと対策（NFR）

- 安全性: ストア更新で型崩れ → `unknown -> zod` 境界と同様に、UI入力の型保証を強化
- 変更容易性: 編集中ドラフトと確定値の二重管理 → 表示側で「ドラフト優先」を一箇所に集約
- 性能: onChangeで再描画増 → 表示整形をメモ化、必要なら debounce
- 運用: E2Eの期待文字列が変わる → data-testid を活用し、意図した断面だけを検証

## Implementation Plan（最小ステップ）

1) コマンドラインの表示がどの state を元に構築されているか特定（同一ストアか、派生計算か）
2) コマンド編集の数値入力イベントを “表示に効く state” へ接続する
   - 保存/キャンセルがある場合はドラフト方式を採用
3) 表示整形関数（フォーマッタ）が数値引数を読むように修正（既に読むなら同期だけ）
4) E2E更新（数値入力→コマンドライン表示更新を検証）
5) `make verify` → `make evidence`、引継ぎ4点を揃える

## Test Plan（証拠）

- 手動:
  - 数値入力後、コマンドライン表示が即更新される
  - 編集キャンセル時は元に戻る（該当する場合）
- 自動:
  - `make verify`
  - `make evidence`
  - E2E: 数値入力→コマンドライン表示の文字列一致
